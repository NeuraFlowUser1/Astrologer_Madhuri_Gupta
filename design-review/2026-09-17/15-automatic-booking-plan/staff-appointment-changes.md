# Staff appointment changes — implementation specification

## Design intent

Extend the practice calendar in /studio so the practice can deliberately cancel an upcoming confirmed appointment, free its time and notify the customer. Cancellation never claims that money has been returned. NeuraFlow's technical role cannot perform this action. Project003 policy and manual-refund workflow are the approved baseline.

## Transaction and downstream specification

Detail lookup accepts the calendar claim UUID; retrieves booking ID internally, current revision, reference, service, customer name, time and state. No receipt secret or payment credentials. Cancellation requires exact Origin, quota, client session revalidated inside the database, operation UUID, claim UUID, expected revision, reason2–500 single-line characters and explicit UI acknowledgement that refund is separate. Database locks session, checkout context, capacity4004002, booking, then delivery jobs, matching finalization order. Under lock recheck future confirmed state and live claim. Journal includes actor hash, reason, original/new revisions, original time, notice seconds and policy guidance. Exact replay returns original result even after state changes; changed body rejects; stale revision rejects. No financial observations, accepted payment or refund amount modified.

In one commit: cancel booking, increment revision, release claim, append audit; enqueue customer/practice cancellation messages and two immutable cancelled workbook rows for the new revision. Calendar cleanup targets the original revision and saved/deterministic event identity. Retain frozen attempted payloads and in-flight leases; existing finish_google_delivery re-enqueues cleanup if a late old meeting creation succeeds. Never overwrite an old attempted email; begin-send revision guards suppress fresh obsolete work and late accepted evidence remains recorded. Post-commit wake is best effort,15-minute recovery remains fallback. Repeated captured evidence for an already accepted cancelled booking must not create a false additional-payment case or reconfirm it; real additional payments/refunds still need review.

Policy guidance: >=24h eligible for full refund review;12–24h staff review because reference does not explicitly grant cash refund; <12h reference offers one complimentary reschedule within14days rather than cash. This cancellation feature does not issue a refund or implement rescheduling. Do not cancel as a substitute for rescheduling: future atomic reschedule must keep the original slot if the new one is unavailable.

## Implementation spec / UI

Reuse existing cream/sage Studio tokens,24px outer panel,16px control text,24px heading,48px minimum buttons and3px focus outline. Each confirmed calendar item adds Manage appointment. Details show factual time, state and policy guidance. Required single-line reason plus unchecked acknowledgement precede Cancel appointment. Pending/uncertain request disables other calendar actions, retains exact body in memory and offers Check same cancellation. No local storage of customer data. Sign-out/role loss clears private details and pending state; request epoch prevents late responses repainting. Server remains authority on eligibility. Reduced-motion/static UI; desktop1440x1000 and mobile390/320 QA.

## Proof before readiness

Synthetic HTTP auth/origin/validation/storage failure; actual development rollback SQL role/replay/revision/financial state/claim/jobs and late Google completion; browser role/privacy, acknowledgement, identical lost-response retry, mobile overflow. No live sends, refunds, production schema or cutover in this implementation. Independent simultaneous-connection and real-provider proof remain separate acceptance requirements.

## Rescheduling specification —29 September continuation

Rescheduling keeps the service, amount, payment and customer identity. Client-only detail + same expected-revision/operation/reason contract, with offset-aware whole-minute new start. Lock context before capacity then booking, recheck session and state, and replace the existing claim interval in one transaction. Conflict leaves original claim and booking untouched. Use current approved calendar policy for weekdays, windows,30-minute step/notice; retain booked duration. Normal advance window10days. Under12hours use the inherited one-time free exception, bounded to14days from that appointment's pre-change start; persist that deadline so later moves cannot extend it. No second late exception. Never reschedule a started/completed/cancelled booking.

Save original and replacement times/revisions in append-only journal. Queue old-revision meeting deletion, replacement meeting, new immutable workbook snapshots and two revision-bound update emails. Reuse booking_ack transport with an explicit rescheduled payload marker and truthful rescheduled copy; do not label it a new purchase. Existing receipt expiry extends to at least new end+24h; no new bearer credential in messages. Frozen/in-flight old payloads remain immutable. Future cancellation after a reschedule refers refund entitlement to staff review rather than granting entitlement by moving the appointment later. A cancelled appointment's exact operation replay must reject operation IDs belonging to a reschedule.

UI: second clearly separated form in Manage appointment,24px h3,16px labels/controls,48px buttons, original time alongside replacement India-time input, explicit no-extra-charge wording, reason required. Exact pending request body and action retained on response loss. Disable all appointment/calendar mutations until resolved. Feedback and list show new time only after successful server response; do not optimistic-move the appointment. Browser proof covers conflict original preserved, lost-response identical retry, server revision conflict and mobile320/390/desktop1440.

## Staff support continuation — implementation specification

Purpose: practice staff can find a saved appointment when the customer lost their receipt, see recorded financial facts, and request another attempt after fixing a delivery connection. Agency access remains limited to its own record copies. A support action never treats a note as proof of payment/refund or issues a public bearer credential.

Private exact-reference lookup uses POST, client session, strict origin, existing durable request limits and no-store. It returns minimum contact/appointment data, current revision, bounded last20 payment observations and outstanding case count. It never returns receipt digests/secrets, Google credentials or provider raw payloads. It can open the existing appointment controls using the saved claim identity, including cancelled history.

Retry reuses staff review revision and actor/operation/reason audit. A distinct action field prevents replaying a note operation as a retry. Same operation returns prior success before issue visibility checks. Changed requests conflict. Lock review item then booking/enquiry then existing job, consistent with workers; reject active leases and accepted/delivered work. Email retry rejects obsolete appointment versions, bounce/complaint/suppression, expired send deadlines and first-attempt age>=23h; never clears provider identity, immutable payload, first attempt, quota reservation or uncertainty. Google retry retains original identity/payload. Payment recheck only schedules authoritative observation through existing recovery; cannot mark a payment case solved or send funds. One support retry per item/minute prevents immediate retry storms.

UI: existing16px labels/body,24px section heading,48px inputs/buttons, rounded panel and focus styles. Exact booking reference input; no broad email/phone search. Inbox retry has its own explanatory button and saves the visible note as reason. Uncertain responses keep original operation body/action and disable new changes until checked. Desktop1440 and mobile390/320 verification; private data clears on role loss. Connection health and backups must not be falsely implied by an empty issues list.

Financial resolution is deliberately narrow: staff may close a payment review only when an immutable provider observation for that exact saved merchant/mode/order/payment shows the whole payment refunded. Partial refunds and missing/mismatched evidence remain open. If the refunded payment is the accepted payment of a still-confirmed appointment, staff must resolve the appointment separately first; this action cannot silently leave an unpaid future appointment or cancel one. Save the evidence observation ID, actor, reason and review revision atomically. Never initiate a refund or accept a typed dashboard claim as provider proof. Repeated observed historical financial events must not reopen an already resolved unchanged case.

## Approved assisted identity procedure and receipt restoration

Owner approved29 September: staff call the mobile number already saved on the booking and verify payment details before changing contact information or replacing receipt access. If that phone is inaccessible, no automatic change; manual staff review. This is an explicit staff attestation, not a claim that this application performs telephony verification.

Implementation: client-only action requires expected booking revision, unique operation, reason, exact saved provider payment ID and explicit completed-verification acknowledgement. Bookings must have captured/refunded provider evidence for that same saved order. Held checkouts are excluded. Contact correction is limited to future confirmed consultations, keeps price/service/time/payment, increments revision, snapshots both old and new destination, revokes old receipt, queues original meeting cleanup and new revision meeting/record/email updates. Existing attempted messages cannot be recalled and are never rewritten.

Receipt restoration never emails a bearer receipt or places one in a URL. After verified phone support, staff receive a purpose-bound8-digit activation code (15minute lifetime, max5wrong attempts, up to3issues/hour/booking). Speak it during the verified call. Customer opens /booking-help and enters booking reference plus code. Their browser creates and saves its new random32-byte receipt secret before requesting redemption; the server stores only its keyed digest. Redemption atomically replaces old receipt digest, resets revocation, gives access through appointment-end+24h or now+24h (whichever is later), and consumes the code. Exact replay with the same saved secret returns the same result; a different secret, old code or later superseding issue cannot replace access. No contact lookup before authentication. Account and booking revision locks serialize issue, correction, reschedule and redemption.

Assisted page: quiet cream/sage existing tokens; max-width720px, heading32–40px, body16–18px, labels16px,48px minimum controls,24px panel corners; no timed popup or autoplay. Separate reference/code labels; clear private-browser-storage errors before redemption; current different booking credential is not overwritten. Stage only opaque request ID/secret in sessionStorage (no activation code, contact data or URL credentials), recover uncertain commit by checking saved secret, promote to normal receipt on success. Desktop1440/mobile390/320; keyboard labels/focus and reduced-motion safe.
