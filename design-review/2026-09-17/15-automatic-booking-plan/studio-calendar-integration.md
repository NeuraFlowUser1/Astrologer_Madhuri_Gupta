# Private calendar controls — 29 September 2026

Design intent: give the practice an understandable view of appointments and unavailable periods in the existing private Studio. This prevents promising time already committed elsewhere. This slice adds viewing and explicit close/reopen only; it does not invent cancellation/refund/rescheduling policy or give agency users appointment powers. Contact remains a separate unfinished package.

Implementation spec: reuse Studio cream #f4f0e8 / paper #fffdf9 / forest #294d40, 856px content width, 48/24px desktop/phone gutters, 24px panels, 24px section title, 16px body/inputs, 14px help, 48px controls. Two-column start/end at >640px, one column below; all dates labelled India time and interpreted at +05:30 independent of device timezone. No assembly on operational forms; stable controls, visible focus, factual success/error status. Inspect1440x1000 and390/320px.

Authority: client-role signed Studio session only. Agency keeps its own connection/record permissions. Every read/mutation rechecks session/client/origin in the database; mutation locks the session against concurrent logout before schedule lock4004002. Wrapper functions with fixed search_path expose only the existing owner-only close/reopen operations; original functions remain ungranted. No new customer mutation route. Existing schedule exclusion and expiry remain authoritative.

Read contract: POST /api/studio/calendar/list with India day and optional opaque UUID cursor. At most50 active claims per page, sorted by claim UUID; day bounded to past31/future366 days. Return only interval, closure reason or appointment name/service/state; no email/mobile, payment identity, receipt material or raw row. Concurrent list changes may require refresh; listing is not an atomic snapshot across pages.

Write contracts: POST /api/studio/calendar/close (operation UUID, reason2–500 chars, aware start/end, maximum31 days and future366-day end); /reopen (operation UUID, claim UUID, reason). Actor derived from signed session, never submitted; the journal uses a SHA256-bound client subject label. Recheck expiry after acquiring the schedule lock. Existing action journal gives immutable operation/body replay and conflict protection. Replayed close returns current active state so an already-reopened period is not falsely described as blocked. Reopen requires active closure (no booking ID), which is a monotonic state transition; stale already-open result cannot change any appointment. Reasons and identity remain server-side audit facts. New idempotency IDs are generated once per explicit action; uncertain requests retain exact payload in memory and disable new mutations until the same request is resolved. Refresh loses that in-memory draft: refresh calendar before making another action; overlap exclusion prevents duplicate closure intervals. No private information persisted in browser storage.

Proof: rejected agency/missing/revoked session, wrong Origin/extra fields/naive dates, interval overlap, exact replay and changed replay, reopen appointment denied, bounded/page-filtered listing, concurrent logout serialization, existing close/capacity exclusion. Rollback SQL on dedicated development only, with runtime-role checks; no production migration. Broader real concurrent sessions remain separately recorded until executed. Frontend browser tests intercept only test requests; no actual staff/Google action.
