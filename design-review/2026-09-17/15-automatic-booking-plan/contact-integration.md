# Durable contact integration — 29 September 2026

Objective: retain contact email verification independently of OTP-free appointment booking. An enquiry is received only after its verified content and delivery intentions commit together. Neither an email-address cache entry, a general-purpose token nor a background thread is authority. Public Contact remains closed on the new system until its actual mail and record consumers and accepted page are connected and verified.

Implementation order: (1) purpose-bound input/crypto, durable verification and enquiry transactions, protected HTTP contracts and adverse-case checks; (2) encrypted short-lived code dispatch, shared Resend budget/recovery/events, client/agency record copies; (3) accepted14 contact design with final same-origin contracts and browser checks; (4) hosted acceptance. These are components of the final system, not temporary hosted systems or mock product wiring. Do not retire the existing caller until its replacement is connected.

Contact intake contract: POST /api/contact/start with client-generated request UUID, mandatory name/email/subject/message and optional international phone. X-Enquiry-Receipt is an independently generated32-byte opaque capability, domain-separated from booking receipts. Freeze the exact payload while a request is unresolved. Only the request ID/capability and optional pending resend operation ID/source generation may be persisted, never form/code content. Bind normalized payload fingerprint, exact email spelling, request ID and code generation. New request requires explicitly open contact intake plus functioning delivery configuration. Existing verified receipt remains readable when intake closes.

Verification: six random decimal digits; HMAC-SHA256 with dedicated protected key, bound to enquiry ID/generation/email/code; five-minute validity, maximum5 incorrect attempts per generation, up to3 generations per request,60-second resend gap. Rate-limit new codes per pseudonymous email and trusted request source with committed limits. Separate opaque receipt required for every resend/check/verify. Verify and save enquiry status plus unique delivery intents atomically; retries can return only the same request's received outcome. Changed content or credential conflicts never mutate the original request.

Secrets: protected SARSA_CONTACT_KEYS JSON with digest (32-byte base64url) and encryption (ordered Fernet keys). Code ciphertext binds purpose/id/generation/email/code; the database supplies and enforces its five-minute expiry. The contact-code consumer checks that saved expiry before decryption and again at send admission. No plaintext code is persisted. No plaintext code in SQL, logs, API errors, subject or persisted message hash. Rotation retains old encryption keys until pending encrypted mail snapshots have drained or reached their deadlines, not merely until five-minute codes expire. Acknowledgement/practice snapshots can remain retryable for23hours. Changing the single digest key requires closed intake and resolution/expiry of outstanding challenges, receipts and encrypted message retries; do not invalidate an existing retry identity. Missing configuration isolates Contact rather than disabling booking recovery. Owner handoff later; never ask for values in chat.

Schema: contact_intake singleton defaults closed; enquiries keep immutable normalized content, receipt/fingerprint, generation and bounded counters; verification ciphertext/digest cleared on success, attempts exhausted or expiry cleanup. Separate enquiry_delivery_jobs use enquiry FK, unique(kind,enquiry,generation), immutable IDs, attempts/next-time/leases/deadline for final workers. No fake booking or borrowing another client's tables. Kinds: verification, acknowledgement, practice_notice, client_sheet, agency_sheet. New generation cancels the old verification job; stale worker completion must be fenced. Enquiry acknowledgement promises saved receipt only, not appointment or actual message delivery.

Cleanup: bounded expiry cleanup callable by recovery consumer; no historical enquiry deletion is introduced without retention approval. Five-minute code expiry is enforced in verification regardless of cleanup timing. Ciphertext erasure is transactional on verify/lockout/resend and scheduled cleanup, not a claim of physical backup erasure.

HTTP safety: exact Origin, trusted source rate limit, JSON bounded by existing16KiB middleware, strict unknown-field rejection, no-store, redacted errors, same-origin callers only. Receipt status exposes only reference, awaiting_verification/expired/locked/received, generation, resend eligibility and server/expiry times; no personal information or secret. Before downstream integration passes, contact routes register but start is unavailable through a disabled delivery-readiness capability; crypto config alone cannot open intake.

Proof for first component: token mismatch/replay/wrong purpose, changed body/email, stale generation, expiry/attempt exhaustion, resend replay, secret-safe responses, closed intake, atomic verified enquiry/delivery-intent creation, DB failure, counters surviving rejection. Rollback-only development fixture under real website role before applying migration023. Component completion does not imply mail/Sheets delivery, production caller migration or hosted readiness.
