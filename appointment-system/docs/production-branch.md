# Production branch and safe default-branch changes

Standard release 1.0.2-rc.1 supports an explicit installation-owned production branch. Existing version-1 monitor.json and backup.json retain their exact main-only meaning. Version 2 accepts exactly the existing public fields plus production_branch; its value must be a bounded ASCII Git-compatible branch name. Unknown fields, malformed refs and missing version-2 branch values refuse. No database schema, saved business setting, provider account or cryptographic archive format changes.

The repository's actual default, event repository default, runner ref and successful export head must all match that configured branch. Public/non-fork/owned-active-repository, standard Linux runner, event/schedule, exact workflow/run identity and credential separation checks remain. The independent monitor still imports no engine/database/provider client. A prod job cannot accept a completed historical main run as prod provenance.

Use tools.automation.production.render_workflow(name, body, production_branch) with the sealed deployment templates to prepare the three receiving workflows. It preserves main output byte-for-byte, pins every pre-run guard to the explicit branch and updates the backup validator's workflow_run branch filter. It refuses unknown or malformed templates. The existing monitor preparation command also accepts --production-branch; conflicts and concurrent owner files remain protected.

For an existing installation, prepare the package through the supported whole-package upgrade in an isolated source/build. A changed digest still needs the documented matching app/Worker/database binding procedure, expected prior identity and idle-worker refusal. Preserve all migration bytes, credentials, settings, original booking intent and queued obligations.

First publish and prove the new release with existing main/version-1 settings. Then prepare the version-2 metadata and generated workflows together on the intended prod branch. Finish any current main export/validation/retention chain. Change the GitHub default and protected job environment restrictions only when that source is ready; align the existing hosting production tracking, prove the actual prod deployment and independent operations, then retire main. Never spoof runner identity, accept an arbitrary branch, turn OFF into cancellation or restore an old database to undo a release.

Historical archives, signatures, keys and immutable release sources stay preserved for independent recovery. New jobs require their configured branch provenance; archival recovery remains a separately authorised isolated operation, not execution of archive-selected code in a privileged current workflow. A live default-branch change requires owner/admin access in GitHub and the correct hosting workspace.
