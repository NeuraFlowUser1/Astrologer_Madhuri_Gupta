Translation records `service_snapshot.meeting = google_meet` on their imported appointments, independently of the new installation's meeting default. Sarsa's original `meeting_platform` label remains in its snapshot; a conflicting explicit platform or meeting choice refuses conversion. This normalization lets later moves and cancellations preserve the accepted meeting obligation through migration 031. It does not create a provider event during import.

The published AstroAdvice 003/16 format has no browser-owned checkout contexts and needs no old context secret. No session, company authority or synthetic sign-in event is created; the original authorisation timestamp remains in the fenced source and its checked fingerprint.

The calendar converter preserves the owned calendar address, deterministic event ID, revision and existing meeting link. It rejects conflicting pointers, foreign owners, changed event IDs and malformed ready links. Older unversioned markers and later versioned markers remain distinct, using saved `protocol_version` when available. Both current booking records and already-queued job snapshots receive the relevant reader. Identical current/versioned event pointers produce one canonical event; conflicting duplicates fail conversion. A preparing/failed source event has no verified meeting link and becomes waiting without creating any new job; its separately translated job retains retry/review uncertainty.

The native AstroAdvice transfer proves the pinned staff identity, encrypted calendar permission and existing event together. ## Retained source privacy (migration 028)

After final native source/target comparison, the offline owner registers each unverified enquiry from the published 004/31 layout. The registration stores only its reference and UTC-stable hashes of the source row and child jobs. It does not duplicate personal content. The source remains fenced against every old runtime. The two original source update guards are replaced, within that final handover transaction, by a common guard that permits only the already-approved erasure fields and preserves all other evidence.

An applied abandoned-enquiry completion clears the canonical and retained copies in the same SQL transaction. A changed or partially missing source rejects the whole operation; the independent intent remains available for review. Both source tables can be absent only in a saved restored generation newer than that handover, as expected for a canonical-only archive. New activity that cancels eligibility leaves both copies intact. Direct writes by maintenance, website, company and retired logins remain denied. Even after a completion, the owner function cannot rewrite identities, provider evidence or restore personal content through this guard.

The new mapping is included in the shipped encrypted backup relation list. Independent privacy replay applies the same source-erasure trigger when an older retained copy is restored. The accepted-only 003/16 enquiry layout receives no automatic abandoned-enquiry deletion path. This does not create a retention policy for accepted business records or old login/verification evidence.
